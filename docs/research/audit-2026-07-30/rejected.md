# What did not survive verification

98 findings were rejected by the verification pass.
They are recorded so nobody re-files them, and so the shape of the false
positives is visible: most are a reviewer not following the code far enough,
or not knowing that something was deliberate.


## ci-release

- **The two release-please components conflict on the shared manifest, and there is no way to re-run the workflow to heal it**
  The mechanical half checks out (the manifest is four lines, `separate-pull-requests: true` at release-please-config.json:3, and adjacent-line edits on two branches do conflict in git), and release.yml really has no `workflow_dispatch`. But the consequence does not follow, and the finding did not follow the trigger through. release.yml fires on `push: branches: [main]`, so merging the first release PR *is itself* the event that re-runs release-please, and release-please recreates its per-component release branch from the new main HEAD on each run rather than leaving the stale branch in place - the manifest edit is recomputed against a main that already carries the other component's bump, and merges cleanly. The claimed recovery ("an empty or unrelated commit on the default branch") is therefore never needed, and even absent that, re-running the previous release workflow run is a button in the Actions UI. There is also no record anywhere in the repo or CLAUDE.md of this ever having wedged. Adding `workflow_dispatch` may still be nice to have, but it is not a finding at high severity, and the "wedged release state with no in-band recovery" premise is wrong.
- **Two independently floating Rust toolchains build the container image and the downloadable binary**
  The facts are right (rust-toolchain.toml is `channel = "stable"`, docker/server.Dockerfile:16 is `FROM rust:1-alpine`, and the binaries link Ubuntu's musl-tools while the image links Alpine's musl) but the harm is asserted, not evidenced: "a miscompile or a codegen-dependent behaviour difference between them is possible and nothing would report it" is a hypothesis with nothing behind it, and both toolchains track the same channel so they agree in practice within a release cycle. Committing `channel = "stable"` to rust-toolchain.toml is a deliberate choice, not drift, and the secondary complaint (a stable roll can turn `clippy -- -D warnings` red on unchanged main) is the accepted cost of that choice for essentially every Rust project. Filing it would send work at a preference. If reproducible builds become a stated requirement it belongs in a decision record, not a defect list.
- **licenses.yml runs a full Flutter toolchain and pub resolve on every push to main regardless of what changed**
  This argues against an explicitly documented decision. docs/ci.md:128 states the design in the finding's own terms - path-gated "on the manifests, the lockfiles and the policy, plus every push to `main` whatever changed" - and docs/ci.md:57 gives the convention it belongs to: "Every push to `main` runs it whatever changed, so `main` is never trusted on a path filter alone." That covers the case path filters miss (a merge whose combined content differs from what any PR run saw), which is not "nothing". The cost is one extra Flutter runner on docs-only main pushes, i.e. minutes, and the finding's own preferred alternative (an advisories check on a schedule) is already filed separately. Nothing here is broken.

  The grep is right (only touch_targets.dart:22 and touch_targets_test.dart:95 construct one) but nothing is contradicted, because the class doc says the width fallback is the intended primary mechanism, not a degraded path: "Falling back to width rather than to a hardcoded false is what makes this unforgettable: a control is at touch density on a phone because of where it is drawn, not because someone remembered to say so" (touch_targets.dart:33-37). `of()` is used by button, icon_button, list_row, menu and focusable_tap_target, so the class is load-bearing; what has no user is a two-field override escape hatch that is documented, tested, and correct when someone needs it. Re-filing it sends work at something already on the ledger. The aggravating claim that makes it worse than absent is also false: AppAction.label has no consumer anywhere in packages/app - the only `.label` hit in command_palette_items.dart:145 is PaletteResultItem.label, a different type - so no keybinding screen exists and nothing is presented to a user as working.
- **AppMenuItem alone has no focusNode, and its 'active' local means enabled where AppIconButton.active means toggled-on**
  Both halves fail. `active` at menu.dart:170 is a private local variable inside build, not an API name, so it cannot collide with AppIconButton's public `active` field at any call site - and it is immediately used as `enabled: active`, which is self-documenting where it is read. The missing focusNode rests on a use case that does not exist: command_palette.dart keeps focus in its AppInput (`focusNode: _focusNode`, line 162) and drives selection with a `_highlighted` index passed to AppMenuItem as `selected: at == _highlighted` (line 239-241) under CallbackShortcuts, deliberately never moving focus down the result list. AppMenuItem taking no node is consistent with the one consumer AppMenu's doc names.

## dart-providers

- **Resuming the app re-registers push on every resume when Android notifications are blocked, because the retry check does not use the _isRegisteredWithServer getter**
  The current condition is deliberate and documented; the proposed fix would break the path it claims to protect. push_controller.dart:370-374, immediately above the code cited, says the resume retry exists so that "a denied permission, a token that had not arrived, or a server that was briefly unreachable all self-heal the same way: try again the next time the user opens the app" - a denied permission is explicitly one of the three. That is the only mechanism by which `registeredNotificationsBlocked` can ever become `registered`: `_applyAndroidResult` (:275-287) decides between the two by calling `_requestAndroidPermission()`, so a user who grants notifications in system settings needs a resume to re-ask. Using `!_isRegisteredWithServer` would strand them as blocked for the rest of the launch. The getter's job is the *lifecycle-report* distinction, which is exactly how the adjacent line :384 uses it, and its own doc says so. The two lines are consistent, not divergent.
- **Two providers do 'listen to liveEvents, invalidate membersProvider' with hand-rolled subscription plumbing each time (seven copies)**
  The count conflates two shapes that cannot share the proposed abstraction. Four of the seven (presence_controller.dart:21/50, pins_controller.dart:46/100, typing_controller.dart:31/64, message_extras.dart:60/253) are StateNotifiers holding `late final StreamSubscription<api.ServerEvent> _sub` and cancelling in a `dispose()` override - the idiomatic shape, which no `Provider.autoDispose` factory or ref-based mixin can absorb. Only the two in member_presence.dart:51-75 and :86-93 use `ref.read(...).listen` plus `ref.onDispose`, and one of them owns a debounce Timer it must also cancel, so a shared factory would save roughly two lines across two call sites. Every one of the seven does cancel correctly, so the stated risk ("each with its own chance to forget the cancel") has not materialised anywhere.
- **PinsController and ChannelSearchController repeat the same mounted-guard / Forbidden / ApiException triple, and their state classes are near-identical**
  "Near-identical" does not survive reading them. PinsState (pins_controller.dart:27-36) has three fields and deliberately preserves the previous `pinned` list through a failure so a header pill never blanks; ChannelSearchState (channel_search_controller.dart:24-44) has six (open, query, results, loading, failed, forbidden) and deliberately discards prior results, and its `toggle()` depends on being replaceable wholesale. A shared AsyncOutcome<T> would have to carry both policies plus the search-specific fields, which is more machinery than the 12 lines it replaces. Two instances is also thin ground for an abstraction, and pins_controller.dart:62-66 already documents the parallel on purpose so the guard cannot be dropped by someone who thinks it is incidental.
- **customEmojiImageProvider is a non-autoDispose family whose doc calls a 500 MiB ceiling bounded**
  The comment it objects to states both multiplicands openly - emoji_catalog_provider.dart:47-49 cites the 500-item cap (MAX_CUSTOM_EMOJI) and the 1 MiB per-image cap (emoji.rs:34, verified) - so a reader is given the arithmetic rather than misled by the word "bounded", and the point being made there is the real one: unlike an attachment cache, this set has a ceiling at all. Reaching 500 MiB requires a deployment holding 500 emoji that are each within a rounding error of the 1 MiB limit *and* every one of them rendered in a single session; a realistic custom emoji is tens of KB. No measurement or symptom is offered, and the finding proposes replacing a documented warm cache with an LRU on the strength of a worst case nobody has produced.

## dart-screens

- **Reactions, attachments and polls hydrate only for the first channel opened, because the State is reused across channel switches (their critical)**
  The premise is stale, and the stale doc comment they quoted is what created it. router.dart:144-150 gives every channel its own page: `fadeThroughPage(context, ConversationPane(channelId: channelId), key: ValueKey('channel-$channelId'))`. A distinct page key makes go_router's Navigator remove the old route and push a new one, so `ConversationPane` and `ChannelScreen` are a fresh element subtree per channel, `initState` runs again, and `_hydrateExtras()` re-fetches `listMessages(channelId, limit: 50)` and calls `applyMessages` for every channel opened - which is exactly what message_extras.dart's own file doc describes ('re-fetching the channel's recent messages on open (see [ChannelScreen]) re-hydrates this cache'). page_transitions.dart:25-27 documents the key's purpose in those words. `git blame` puts the 'builds this widget with no key' comment at dca58e6 (2026-07-27) and the per-channel page key at ca1669b (2026-07-29), so the comment simply outlived the routing it described. Everything downstream of the premise - #general then #random rendering blank polls, `key: ValueKey(channelId)` as a fix - does not happen. The comment itself is filed as a confirmed low finding instead.
- **Three admin list screens repeat the same scaffold-plus-async-list-plus-busy-card skeleton verbatim**
  What repeats is a call to a shared component with its arguments, which is the componentised form, not duplication awaiting extraction. `SettingsScreenScaffold` already exists for exactly this and all seven settings/admin screens use it; `AppAsyncView` already owns loading, error, empty and data. The residue is six named arguments (title, backTooltip, backFallback, errorMessage, emptyMessage, separator gap) that differ per screen because they are the screen's content, plus a `ListView.separated` that differs in item type. An `AdminListScreen<T>` taking title, provider, errorMessage, emptyMessage, separator, itemBuilder and actions is seven parameters of indirection to save eight lines of declarative configuration, and would put the type parameter between a reader and the list. The one piece genuinely worth deduplicating is small and specific: `backTooltip: 'Back to Space settings'` with `backFallback: Routes.spaceSettings` at six of the seven call sites could be the default when the caller gives neither. Filed at that scope it would be a trivial cleanup, not a medium componentisation finding, and their own claim that 'the twenty lines above it are boilerplate' does not survive counting them.
- **debug_log_screen passes AppTokens down as a constructor argument while the widget beside it reads Theme.of**
  No defect, and the two supporting claims do not hold. They concede there is no live bug (the parent reads `Theme.of(context)` in its own build, so a theme change rebuilds it and therefore its children). 'Unusable anywhere the caller has not already resolved tokens' is not true of a caller that can write one line to resolve them. And it is not the lone outlier: tokens are threaded as parameters in three other files - presence_menu.dart:135 `_buildMenu(AppTokens tokens, ...)`, command_palette_items.dart:106 and command_palette.dart:201 - so `_EntryTile` is unusual only in taking it through a constructor rather than a method. Threading a resolved theme extension into a list item that is rebuilt in a tight loop is a defensible choice, not a mistake, and there is no project rule against it. Filing it sends work at a preference.

## dup-server

- **The batched/per-user permission equivalence is asserted only for VIEW_CHANNEL, which is structurally the one bit that cannot detect the timeout divergence**
  Refuted: the guard exists in a file the auditor did not open. `crates/slimm-server/tests/it_spaces/member_timeout.rs` contains two tests that cover exactly the two claimed gaps. `the_batched_timeout_lookup_matches_the_single_one` (line 233) compares `timed_out_among_until` against `timed_out_until` per id, including a user with an already-elapsed timeout and the empty-candidate case — that is a direct assertion on the very divergence the finding calls 'structurally invisible'. And `the_batched_paths_agree_with_the_per_user_path` (line 140) sets a real timeout, then drives `viewers_among` and `visible_channels` against `has_permission` across both a text channel and a DM. Its doc comment states the auditor's own observation as deliberate: 'Both only ask about VIEW_CHANNEL today, which a timeout deliberately does not touch, so the outcome here is "nothing changes" - and that is exactly the point: a timed-out member must keep receiving pushes and keep seeing their rail.' The narrow factual claim ('there is no timeout anywhere in tests/it_spaces/permissions.rs') is true but does not support the conclusion, because equivalence for the timeout rule is pinned elsewhere. `a_timeout_reaches_direct_messages` (line 113) and `an_administrator_is_masked_like_anyone_else` (line 262) close the remaining dimensions.
- **Two competing conventions for mapping store errors to ApiError, split eight to thirteen, with the same Internal arm repeated in every one**
  The counts are accurate but the harm is not. The split is not arbitrary: I grepped every one of the error types and the four store types with `From` impls in error.rs (`HashError`, `SendError`, `PushError`, `OpenError`) appear nowhere in src/http outside error.rs — their handlers use bare `?` and never name the type, which is precisely why they need the impl. The twelve matched inline are all matched in the one module that owns their route, and every non-Internal variant produces a message phrased for that route ('the @everyone role cannot be deleted', 'this would leave the deployment with no administrator', 'that search query is not valid'). So the working rule is 'a From impl when the mapping is route-independent, an inline match when the refusal needs route-specific phrasing', which is coherent rather than accidental. The two concrete harms both fail: 'thirteen chances to map an internal error to something other than a 500' is theoretical, since every one of those arms is literally `e.into()` reaching the same `From<anyhow::Error>`; and 'half the store's failures lose their context in the log' is overstated, because the store attaches `.context(...)` to the anyhow errors it wraps (e.g. store/pins.rs's 'loading a message to pin it'), which `tracing::error!(error = %err)` prints. Nothing here is a defect, and mechanically collapsing twelve inline matches would move route-specific wording away from the route that needs it.
- **Seventeen source files are over the 300-line review budget; the two past the 500 hard limit are registered but their named seams are still uncut**

## sec-input-dos

- **Sub-claim: POST /sync can drive roughly 2000 sequential queries from one request**
  Arithmetic is right per scope (~10 queries) but the 200x multiplier is not reachable without 200 distinct channels the caller holds VIEW_CHANNEL on, which a small self-host does not have. With nonexistent channel ids the cost is 2 queries per scope (`granted_in_channel` returns early at `channel()`, `timeout_deny` still runs as the argument to `.remove()`), so the floor any member can reach is ~400, not ~2000. The finding survives with corrected arithmetic; the 2000 figure should not be quoted forward.
- **Sub-claim: the Upload rate limit 'cannot protect the resource it exists to protect'**
  `ratelimit.rs:48` states the resource Class::Upload protects is disk, and disk is protected: `media.write_attachment` at attachments.rs:118 runs after both `enforce` and the ATTACH_FILES check, and `attachments::routes(max_attachment_bytes)` applies `DefaultBodyLimit::max(...)` so the buffered body is bounded at the operator's configured ceiling. What the ordering actually exposes is memory and bandwidth for a refused caller, which is a narrower claim. Folded into the confirmed HTTP-bounds finding with corrected wording.
- **Sub-claim: viewers_among's DM N+1 is 'on the message send path'**
  It is not. `PushSender::notify_message` (push.rs:148-166) hands the recipient lookup to a detached `tokio::spawn(deliver(...))` and its doc comment says so: 'Synchronous and cheap ... the recipient lookup, lifecycle gating, per-recipient debounce, sealing, and relay call all happen in a detached background task, so this never blocks or fails the caller.' The N+1 is real and the two comments describing it are wrong, but it does not add latency to a send, which is why the finding is confirmed at low rather than medium.
- **Sub-claim: pins::routes() sets no DefaultBodyLimit, unlike every other route group**
  True as stated but not a defect. axum applies a 2 MB default body limit when no `DefaultBodyLimit` layer is present, and none of the three pin routes takes a request body at all (`put`/`delete` on the pin path and two `get`s). Dropped from the pins finding so it does not read as a missing bound.

## sec-server-authz

- **A role-granting invite can be redeemed by an existing member, so sharing an invite link escalates anyone already inside**
  The mechanism is real (redeem at http/invites.rs:242-257 requires only authentication, and store/invites.rs:216-238 applies `role_grant` to whoever asked), but it is not a distinct authorization flaw and the framing does not survive. A role-granting invite is a bearer credential whose documented meaning is the role: tests/it_accounts/invites.rs:615-618 states it as "an invite's role is who redeeming it becomes", and store/invites.rs's own doc on `spend_invite` names "redemption by an existing account (Store::redeem_invite)" as one of the two intended paths sharing that statement. The finding's own justification — "a caller that passes an empty or permission-filtered group list (which is exactly how Space settings is described as behaving for an unprivileged caller)" — is factually wrong: `SpaceSettingsScreen` returns `SettingsScreenScaffold`, not `SettingsPanesScaffold` (space_settings_screen.dart:19), and its permission-filtered empty case is handled by `SpaceSettingsSection` returning `SizedBox.shrink()` (space_settings_section.dart:45-47) in a completely different frame. A defensive `SizedBox.shrink()` guarding an impossible state in a widget with one caller is not a defect, and adding an empty-state message for a caller that does not exist is speculative work. If Space settings is later moved onto this scaffold (see the two-settings-languages finding), the empty case becomes worth handling then.

## ui-space-settings

- **Desktop wastes about half the panel: fixed 72pt rows ignore the design system's density pair, and a 360pt text column sits in an 860pt panel**
  The density half is a measurement artifact of the snapshot harness. `main.dart:114` wraps the entire app in `ListTileTheme.merge(dense: !AppTouchTargets.of(context))`, with a doc comment stating exactly the problem they are re-filing: "Material's own list rows are sized for a thumb whatever the window, which is what made the settings and administration screens read as a phone blown up. Applied here rather than per screen so a new one cannot forget, and read from the window so nothing has to say which." `AppTouchTargets.of` falls back to window width against `kCompactWidth = 600`, so the shipped desktop app renders these rows dense. The harness (ui_snapshot_test.dart:96-107) builds a bare `MaterialApp.router` with no `builder`, so the 72.0pt pitch they measured exists only in the PNG. Their proposed remedy is also wrong in kind: `AppListRow` has no subtitle slot at all (label, leading, meta, trailing, selected, unread, muted, touch, height, onTap) and `AppSizes.rowPointer = 30` cannot hold a two-line row, so converting would delete the subtitles - which their own summary calls the best copy in the app. The horizontal half misapplies `content_column.dart`'s doc comment: that comment is about a label at one end and its VALUE at the other, and the thing 368pt away here is a chevron, a pure disclosure affordance at the trailing edge by universal convention, not information to pair with the label. The only real residue is that the panel is a fixed 720pt with 178pt (25%, not "roughly half") empty below the content, which is confirmed separately as the fixed-panel-height finding.
- **Seven flat peers with no grouping and no state (the grouping half)**
  The absence of a group header is deliberate and documented at the top of the file they cite. space_settings_section.dart:6-7: "This is [SpaceSettingsScreen]'s whole body, not a section sharing a screen with personal settings, so it owns no group header or divider of its own." Comparing it to personal settings' `SettingsPaneGroup` labels is comparing a body to a nav: personal settings is a nav-and-pane scaffold where the groups label nav entries, and this screen has no nav. Their own summary concedes the link-list shape is "a defensible shape" because the six destinations are full CRUD screens with their own app bars and `modalPage`, which is the correct read. The `SettingsPane.badge` evidence is also misattributed - `badge` is a field on the personal-settings nav's `SettingsPane`, a widget this screen never constructs, so it being "unreachable from here" is trivially true and not a defect of this screen. The one substantive part, that Reports carries no count of pending items, survives as its own narrowed finding.
- **"Who can join" is visually the odd row out because its subtitle names its colour**
  Backwards, and it double-counts. This is the one row on the screen whose subtitle is the CORRECT colour: `tokens.textSecondary` is #A7AEB6 dark / #5B6169 light and that is exactly what line 96 sets and what I measured (633px of it in each render). The six neighbours are the wrong ones, painting Material's `onSurfaceVariant` at #C0C8CD / #40484D because there is no ListTileTheme - which is the ListTile-colour finding, already filed. Filing this as "the odd row out" would send someone to delete the one correct colour on the screen. Their direction even says so in passing ("or, better, fix all seven at once") while the title and severity say the opposite. Their measurement direction is also wrong: they call it "visibly lighter in dark", but #A7AEB6 is darker than #C0C8CD, so it is dimmer in both themes, not lighter in one. The row rendering as a `ListTile` rather than `SettingsSelectRow` is separately deliberate and documented twice (join_policy_row.dart:4-8 and settings_select_row.dart:48-50). The copy half - two names for one setting, mixed subtitle modes - survives as its own finding.
- **A failed join-policy change vanishes as a SnackBar, a 28th site**
  Not a defect of this scope, and the "28th" framing is wrong. `showSnackBar` has 26 call sites across 16 files in the app package, including the mutation-failure paths of roles_screen, invites_screen, reports_screen, emoji_screen, channel_overwrites_screen, member_actions, presence_menu, avatar_settings_section and composer. So a toast on a failed write is the app's prevailing pattern, not a lone omission - the `AppErrorState` sweep CLAUDE.md records converted failures that were only ever a toast on load and read paths, and `error_state.dart`'s own doc comment names the cases it was written for ("a failed account deletion or a failed block"). Whether mutation failures should also be persistent is a real app-wide question, but singling out one of 26 as a space-settings finding would send work at one line and leave 25 peers, and would be quoted forward as though this screen were the outlier. Worth noting the cited path is not silent either: it records to `debugLogProvider` first (join_policy_row.dart:53-55), which is more than most of the 26 do. File it against the pattern or not at all.
- **The near-empty panel's zero-permission case is unreachable in practice (their reachability reasoning)**
  Recording this as a partial rejection because the finding survives but its reachability argument does not, and the corrected version is materially different. They argue reachability turns on "/settings/space is a plain path in a web build, so a bookmark or a pasted URL reaches it" - true but marginal. The stronger fact they missed is that `myPermissionsProvider` is `ref.watch(meProvider).valueOrNull?.permissions ?? 0` (admin_providers.dart:25-27), so the same empty branch is the LOADING state, and every cold navigation renders the titled empty panel until /me answers regardless of who is looking. The confirmed finding carries the corrected reasoning.
