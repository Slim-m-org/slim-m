# Web backlog

See [README.md](README.md) for what "confirmed" and "suspected" mean here and how this differs from `docs/BACKLOG.md` and `docs/OPEN-QUESTIONS.md`.

Read `client/packages/app/web/README.md` before anything else in this file - it states the web build's purpose: driving the UI automatically, and (since decision 0025) the `slim-m-web` image the live host serves.
The web build exists so this project's own e2e harness (`scripts/e2e.sh`) can drive the UI headlessly through Chrome DevTools Protocol, because a native Linux build cannot be driven by synthetic input on this project's Wayland desktop.
That framing matters for reading every entry below: several of these are findings from *using the web build as a test harness*, not from treating it as a real deployment target end users are meant to reach, and some entries below are explicitly about the harness rather than the product.

## Confirmed

**`dart analyze` and `dart format` do not catch a conditional-import symbol mismatch that only fails on `dart2js`, and this has already shipped broken once.**
`client-ci.yml`'s own comment on the "web compiles" step: "dart2js resolves conditional imports that `dart analyze` never does: a symbol present in one branch of a `dart.library.js_interop` export and missing from the other compiles fine here and fails only on web. That is exactly how main shipped a web build that could not compile, with analyze, format and every test green."
*The rule to keep*: `flutter build web --release` is its own required CI step for exactly this reason; do not treat a green `dart analyze` as proof the web build compiles.

**Two binary build inputs the web build needs at runtime are deliberately not committed to the repository, and a checkout that never fetched them fails silently at runtime rather than at build time.**
the pre-trim `CLAUDE.md`, "What a gitignored build input costs on a fresh checkout": `sqlite3.wasm` and `drift_worker.js` (fetched by `client/packages/app/tool/fetch_web_assets.sh`, documented in `web/README.md` above) are static files copied into `build/web`, not compile inputs, so `flutter build web` succeeds with zero warning even when they are absent.
The only symptom is at runtime: `WasmDatabase.open` throws on the 404, the channel rail renders "Could not load channels," and `SyncController` never starts, so the connection bar reads "Offline, retrying" - while everything served straight off plain REST (sign-in, the member pane, settings) keeps working, which is exactly why a missing-asset failure first read as a messaging regression rather than a missing file.
`scripts/e2e.sh` now runs the fetch itself and checks the running origin serves `main.dart.js`, `flutter_bootstrap.js`, `sqlite3.wasm` and `drift_worker.js` by name before proceeding.
*The rule to keep*: any script or process that builds the web target for the first time on a fresh checkout must run `tool/fetch_web_assets.sh` first; do not assume `flutter build web` alone is sufficient.

**A stale build directory silently serves an old bundle even after fetching the missing assets, with no warning.**
`CLAUDE.md`, same entry: `flutter build web` copies `web/` into `build/web` once and does not re-sync a file that appears in `web/` later, even on a full rebuild that recompiles everything else - so fetching the two binaries into an already-built tree left them out of the served bundle, with `✓ Built build/web` printed and nothing to say otherwise.
`E2E_REBUILD` (an env var the e2e harness reads) removes `build/web` before building for this reason.
*The rule to keep*: after adding or changing a file directly under `web/`, remove `build/web` before the next build, or the new file will not reach the served output despite a clean build log.

**A live static file server that discards its own bind failure can silently serve stale content instead of failing the run.**
`CLAUDE.md`, same entry: `python3 -m http.server` swallows a bind failure, so a leftover server already listening on the harness's port answers instead of the new build, and a run can screenshot a build it never actually compiled. The harness now refuses to start when the port is already answering. This is worth knowing for anyone standing up a web build manually with the same tool for local testing, not just the harness.

**The Flutter web accessibility tree is genuinely different from native, in ways that both affect the e2e harness and are a real signal about assistive-technology support in a browser.**
the pre-trim `CLAUDE.md`, "A voice call has been held, and it is a script now": Flutter paints to a canvas on web and exposes nothing to the DOM accessibility tree until a click on a placeholder node it leaves behind; only the currently-focused text field gets a real `<input>` element, every other field is paint reached only by its `aria-label`; and the same visible label can be painted onto both a plain node and a separately-hittable tappable node, where only the one carrying `flt-tappable` or `role="button"` actually responds to a click. These are stated as harness-driving facts, but they describe exactly what a real screen reader or browser extension sees too, since both read the same DOM tree the harness does.

**The channel rail published no accessibility nodes at all on web, and the root cause was a modal barrier silently suppressing an unrelated, already-painted sibling subtree - a bug class, not just a bug.**
the pre-trim `CLAUDE.md`, "Current state," and confirmed fixed in `client/packages/app/test/shell_semantics_test.dart`, which reproduces it with no browser at all: a full-screen `BlockSemantics(blocking: true)` inside the conversation pane's own nested navigator dropped every semantics node painted *before* it in the whole tree, not just its own subtree - the rail (painted first) vanished, the member pane (painted after) did not, and every rail widget tested in isolation passed, because the interaction only appears when the whole shell renders together. Fixed by giving the conversation pane its own semantics node to contain the block.
*The rule to keep, stated directly in `CLAUDE.md`*: "a modal route's `BlockSemantics` reaches backward across whatever else the tree painted first, not just its own subtree, so any future full-screen barrier needs the same containment or it silences its older siblings." Any new full-screen modal/barrier widget added to the app needs the same containment check, and a regression here is one that individual widget tests structurally cannot catch - only a full-shell render can.

**Per-participant call volume (`Helper.setVolume`) silently does nothing on web, and there is no error to catch because the platform API itself has no relevant handle.**
the pre-trim `CLAUDE.md`, "Moderating a member": "Web silently does nothing. It becomes `applyConstraints({'volume': ...})`, which no browser honours, and `applyConstraints` constrains a track's *source* - a remote track's source is the RTP receiver. LiveKit plays remote audio through an `HTMLAudioElement` it does not expose, so there is no other handle." `client/packages/rtc/lib/src/audio_gain.dart`'s `supportsParticipantVolume` correctly excludes web via its `lk.PlatformType` allow-list (Android, iOS, macOS only; confirmed by reading the file), so the control is absent rather than present-and-broken.
Worth restating a line from that same `CLAUDE.md` section directly: "Fedora and the web build are two of the three that cannot do it, so the feature is invisible in both environments this project tests in locally, and real only on a phone" - a contributor working purely against the web build will never see this control, by design.

**There is no per-window screen-share picker on web because a real one already exists via `navigator.mediaDevices.getDisplayMedia`, and this project's own desktop source-listing logic is deliberately not exercised there.**
Confirmed by reading `client/packages/rtc/lib/src/desktop_sources.dart`: `WebrtcDesktopSources.required` is `lk.lkPlatformIsDesktop()`, which is false for a web build, so `list()` returns immediately with no enumeration at all on web - the browser's own native picker (invoked by the underlying `getDisplayMedia` call) is the only chooser, the same shape as the Wayland-portal case for Linux, and unlike the desktop-native builds (macOS, Windows) that must show this app's own sheet.

**Screen-share audio (2026-08-13) is real on web, source-verified through the whole chain rather than assumed from the W3C spec alone.**
`dart_webrtc`'s `MediaDevicesWeb.getDisplayMedia` (`mediadevices_impl.dart`) `jsify()`s the entire constraints map straight into the browser's own `navigator.mediaDevices.getDisplayMedia`, `audio` included with no translation or stripping - this project's `includeAudio` flag reaches the real browser API unmodified.
`client/packages/rtc/lib/src/screen_share_audio.dart` is the capability seam; `supportsScreenShareAudio` includes web unconditionally, on the reasoning that a browser without support (Firefox, Safari) simply returns no audio track and `livekit_client`'s own `createScreenShareTracksWithAudio` already checks `stream.getAudioTracks().isNotEmpty` before publishing one, so the degradation is silent and identical to today's video-only share - never an error a user would see.
*Not itself checked here*: which real browsers actually honour the `audio` constraint and under what conditions (tab audio versus whole-screen system audio), since that is standard, well-documented browser behaviour rather than something this project's own source controls; Chromium-family browsers are the ones known to support it.

**CORS is opt-in and off by default, and a web build served from any origin other than one the server explicitly allow-lists cannot reach it at all - deliberately, not as an oversight.**
the pre-trim `CLAUDE.md`, "Cross-origin access, moderation UI, and channel administration": `SLIMM_CORS_ALLOWED_ORIGINS` adds an opt-in CORS layer; unset or empty means **no CORS layer is added at all**, not an empty allow-list, "since an empty `CorsLayer` would still intercept preflights and answer them without an allow header, which is a different, worse thing than refusing to add it." `*` is refused at startup by design, reasoned in that same section as protecting a self-host's LAN perimeter from every page a browser on that network happens to visit. A native (non-web) client sends no `Origin` header and is entirely unaffected either way.
*Practical consequence*: standing up a web build against a self-hosted server for the first time and getting a silent network failure is very likely a missing `SLIMM_CORS_ALLOWED_ORIGINS`, not a client bug.

**Web is the one platform where Ctrl+V pasting an image just works, with no permission prompt, because the browser's own `paste` DOM event hands over the bytes directly - the opposite of every native platform, where a picker or a native paste gesture is required.**
`docs/BACKLOG.md`: "Flutter's own `ClipboardData` carries only `text`... so there is no cross-platform clipboard image to read. The web build hooks the browser's `paste` event, which hands over the bytes and needs no permission prompt (unlike `navigator.clipboard.read`). On desktop and mobile the file picker is still the only route." This is the one clipboard-image path in this project that is *simpler* on web than natively, and it is worth not accidentally "generalizing away" if the native paste paths are ever revisited.

**Text selection within a message is gated by `TargetPlatform`, not by window width or `kIsWeb`, which is a deliberate design choice worth knowing before "fixing" it to look at the platform differently.**
`client/packages/app/lib/src/features/messages/widgets/transcript_selection.dart`'s own doc comment, confirmed by reading the file: `supportsTextSelection` excludes only `TargetPlatform.iOS` and `TargetPlatform.android`, explicitly reasoned as "the platform is the right question rather than the window width: a narrow desktop window still has a mouse, and a tablet in a wide layout still has no right button." Since Flutter web derives `defaultTargetPlatform` from the browser's own platform detection, a web build accessed from a mobile browser correctly falls into the touch-excluded branch without any web-specific code; this is stated here because it is easy to assume `kIsWeb` should gate this instead, and doing so would break the mobile-browser case.

## Suspected

**Whether Flutter's `WidgetSpan`-based markdown inline elements (mention chips, inline code, spoilers) survive a text-selection copy on a desktop browser has never been checked, positively or negatively.**
`docs/IMPLIED-GAPS.md` item 8: `TranscriptSelection` wraps the transcript in a plain `SelectionArea`, added before markdown's `WidgetSpan`-based inline elements existed, and "Flutter's default handling of a `WidgetSpan` under selection does not guarantee the visible content round-trips through copy unless the span opts into selection explicitly." No test exercises selecting across one of these spans on any platform, web included, which is where `SelectionArea` matters most, since desktop-browser copy-paste is a primary interaction there.

**Whether real assistive technology (a screen reader running against Chrome, not just the e2e harness's own DOM-reading script) can actually use the web build end to end has never been checked as its own pass**, distinct from the semantics-tree bugs found and fixed as a side effect of building the e2e harness. The confirmed entries above establish real, fixed structural bugs in what the accessibility tree contains; none of them constitute a dedicated screen-reader pass of the kind the "nine-specialist audit" ran for visual and interaction concerns.

**There is no web push notification path of any kind, and whether this is a deliberate scope decision or simply unaddressed is not stated anywhere in the project's docs.**
Confirmed by absence: no service worker, no `manifest.json` push/notification configuration beyond the standard PWA manifest, and no web-specific registration call anywhere in `client/packages/platform/lib` (which handles APNs and FCM registration for iOS and Android specifically, with no web equivalent). Given the web build's own stated purpose ("a test surface, not a distribution target"), this is very plausibly intentional rather than a gap, but no document confirms that reasoning explicitly, so it is recorded as suspected-by-absence rather than assumed settled.

**Whether the web build is safe or supported as a genuine end-user deployment target at all, beyond its stated role as a test surface, is unresolved.**
This follows directly from `web/README.md`'s own framing quoted at the top of this file. Nothing in `docs/ROADMAP.md`'s Phase 9 release-readiness deliverables names a hosted web deployment as a release artifact, alongside the store and packaging targets it does name. Treat any request to "ship the web build to real users" as a scope question for `docs/OPEN-QUESTIONS.md` or `docs/BACKLOG.md`, not as something this backlog file's entries assume is already intended.
