# What slim-m does today

This is an inventory of the product as it actually stands, derived by reading the server's route table (`crates/slimm-server/src/http.rs` and `http/*.rs`, gated against `schema/openapi.yaml`) and the client's screens, routes, and providers, not by reading the planning docs.
`docs/BRIEF.md`, `docs/STRATEGY.md`, and `docs/ROADMAP.md` describe the product that was planned; this describes the product as it stood on 2026-08-11, at server 0.37.0 and client 0.39.0.
It has not been re-derived since, so read it as a floor rather than as current: everything in it shipped, and a great deal has shipped after it that is not here.
`.release-please-manifest.server.json` and `.release-please-manifest.client.json` hold the current versions.
For what exists now, read `schema/openapi.yaml` for the wire surface and `docs/decisions/` for each feature and why it is shaped the way it is.
`CLAUDE.md` is a short durable-context file; the history of how each thing got that way lives in git and `docs/`.
This file is meant to be re-derived the same way, not hand-maintained by memory.

## What it is

From `docs/BRIEF.md`: a lightweight, cross-platform, open source messaging platform with optional self-hosting, recreating the core Discord experience (group chats and direct messages with text, voice, and screen sharing) rather than cloning it feature for feature, with an infinite collaborative Voice Canvas during calls as the signature feature.
It ships as a Flutter client (iOS, Android, Linux, plus a web build served by an optional `slim-m-web` image, see `docs/OPERATING.md`) talking to a single Rust server process with an embedded SQLite database, plus a separate stateless Go push relay that only wakes backgrounded mobile clients.
One deployment is one community: there is no multi-tenant hosting and no federation between deployments.

## Capabilities today

Every item below says where a person actually reaches it from, not just that the server has a route for it.
Where the reachability trap this project has hit before (an endpoint with no call site) mattered, it's called out.

### Talking

- **Channels, categories, and DMs.** Text channels, voice channels, and direct messages, all `channels` rows distinguished by `kind`. Channels can be grouped into drag-reorderable categories (`docs/decisions/0006-channel-categories.md`), created from the Space menu's "Add channel"/"Add category" items. A DM with yourself renders as an ordinary DM titled "Notes" rather than a special-cased channel, reached from the rail like any other conversation.
- **Threads.** `docs/decisions/0005-threads.md`: a thread is a channel with a `parent_message_id`, not a separate table. Opened from a message's context menu ("Reply in thread") or from the "N replies" affordance under a message that already has some, both routing to `/thread/:channelId`. Permissions, sync, push, and search all fall out of a thread just being a channel; nesting a thread inside a thread is refused server-side (400). A live socket event (`ThreadUpdated`) keeps the reply count and last-reply time fresh for anyone already viewing the parent.
- **Replies.** A message can quote another message inline (`messages.replyToId`); tapping the quote jumps to the original. This is the lighter mechanic threads were built beside, not a smaller version of them.
- **Reactions, pins, polls.** Reactions are per-viewer filtered (a blocked reactor's tally is invisible to you, and reactor identity is never on the wire frame). Anyone who can read a message can ask who left a reaction, through a per-viewer list filtered exactly like the tally ([0051](decisions/0051-who-reacted.md)). Pins are a moderation action gated on `MANAGE_MESSAGES`, capped at 200 per channel, refused rather than silently truncated past that. Polls are single-choice, 2 to 4 options, sent as a message rather than a separate resource.
- **Search.** Per-channel full-text search (SQLite FTS5) over that channel's messages, supporting FTS5's own mini query language (`AND`/`OR`/`NOT`, `"phrase"`, a trailing `*` prefix). There is no cross-channel search and no advanced operators (`from:`, `in:`, `has:`, `before:`/`after:`, `filename:`); that's a backlog item, not built.
- **Markdown.** Bold, italic, strikethrough, and spoilers inline; headings, quotes, and ordered or bulleted lists as blocks. No toolbar: it's typed markers (`**bold**`) plus keyboard shortcuts (Ctrl/Cmd+B, Ctrl/Cmd+I), with Enter continuing a list and closing it on an empty item. Hand-rolled parser rather than a markdown package, because the existing mention chips, custom emoji, and inline code widgets predate it and a document-rendering package can't produce them.
- **Message jump.** Search results, pinned messages, the command palette (`Ctrl+K`), and the report queue all navigate to a message and flash-highlight it, through one shared function rather than four separate implementations.
- **Edit, delete, and message reconciliation.** Edit and delete are authorship-gated (edit also allows `MANAGE_MESSAGES`). An edit that changes nothing writes no history and shows no "(edited)" marker. A separate op stream (`message_ops`) makes edits and deletes made while a client was offline actually reconcile on reconnect, closing what used to be the project's oldest correctness debt.
- **Attachments and image paste.** Attachments are content-addressed by sha256 for dedup, sniffed from bytes rather than trusted headers. Image paste into the composer works differently per platform: confirmed working on a real iPhone via the system long-press edit menu with no permission prompt; a "+"-sheet fallback row exists on both iOS and Android (Android's route is unit-tested only, not confirmed on real hardware); the web build listens for the browser's own paste event; desktop (Linux, and macOS/Windows if built) has no clipboard-image handler at all and falls back to the file picker.
- **Custom emoji and reactions.** A searchable, grouped, keyboard-navigable emoji picker mixing the deployment's custom emoji with a recents shelf. Custom emoji upload is `MANAGE_SERVER`-gated.
- **Read state and unread.** Own-device read markers sync through `/sync`; unread counts are derived on demand rather than separately counted. Read receipts visible to other users are deliberately not built (owner decision, deferred).
- **Notification sounds.** Seven distinct sounds (DM, mention, group message, member join/leave, call ring, error) play in-app, foreground only, one trigger each, muted for a call above roughly 8 participants and for your own actions. Toggled from Voice settings (join/leave, ring) and Personal > Notifications (messages/mentions/errors). No per-platform background sound, CallKit ringtone, or Android notification channel yet - foreground-only is the whole of what's built.
- **Command palette and shortcuts.** An in-app-focused quick switcher (`Ctrl+K`) and user-remappable keyboard shortcuts, both reachable from any screen and bound into the shell.

### Voice, calls, and the canvas

- **Voice channels.** 1:1 and group voice plus screen share over a self-hosted LiveKit SFU. There is no join lobby: clicking a voice channel connects directly, and the rail shows a live roster of who's already in a channel before you join it. Whether your camera turns on when you join is a persisted Voice Settings toggle, applied automatically at join and at app startup rather than asked per call.
- **Calling in a DM.** No new route and no per-DM room provisioning: a DM channel is a channel, so it only needed `CONNECT`/`SPEAK` added to the permissions a DM's two participants already hold. Reached from a phone/call icon in the DM's header (both the wide and compact layouts), which swaps the conversation body for a call pane wrapping the same voice screen a real voice channel uses. There is still no ringing: nothing pushes a wake for an incoming DM call, so both people effectively have to already be looking at the app.
- **Screen share.** Works, with platform-specific traps worth knowing rather than a flat "it works". On Linux enumerating *windows* (not screens) on Wayland segfaults the process, so that path is never called, and a screen share now stops when a call ends on every path (hang-up, forced disconnect, sign-out) via LiveKit's own unconditional track teardown - traced end to end through the exact `livekit_client` version this client locks, but not confirmed against a real desktop's recording indicator. On iOS, both the double-capture collision (ReplayKit extension plus flutter_webrtc both trying to start a capture) and the "stayed recording after hang-up" bug have source-reasoned, unit-tested fixes; neither has been confirmed on a real device.
- **Per-participant volume.** Works on Android, iOS, and macOS. Throws on Linux and Windows (a flutter_webrtc limitation: those platforms never populate the map the lookup depends on). Silently does nothing on web (there's no handle to a remote track's audio element to apply gain to). The slider is hidden on platforms where it wouldn't do anything, including Linux, which is one of the project's two local dev and test targets.
- **Camera.** Capture works, with the join-time toggle above. Background blur or replacement does not exist; the owner has called it close to a requirement, not a nice-to-have, but it needs a per-frame segmentation model and hasn't been started.
- **The Voice Canvas.** Substantially past a first slice now. A shared collaborative surface with a real toolbar: place strokes, shapes, text notes, and pasted images (`POST /channels/{id}/canvas/objects`); move and resize any object (the `move`/`reorder` ops); erase your own object or, with `MANAGE_CANVAS`, someone else's; clear the visible canvas; and undo (`restore`, an inverse op rather than rewriting history). A timeout freezes the pen but never the eraser, so a timed-out member can still remove their own ink. Camera bubbles and screen-share tiles are real, first-class canvas objects now (`docs/decisions/0010-canvas-media-tiles.md`) - world-anchored, movable, resizable, and lockable by anyone holding `VIEW_CHANNEL`/`USE_CANVAS`, not screen-pinned corner widgets. Multi-user cursors, a text-based activity log (an accessibility fallback for the drawing itself), collapse-to-strip on leaving the canvas, and a fullscreen mode that drops all chrome but the call controls are all built. Whether a canvas is meant to be permanent per channel, a per-call artifact, or something cleared by hand is still an open product question (`docs/OPEN-QUESTIONS.md`); the schema only expresses "permanent per channel" today, which is what's shipped.
- **Android voice.** Declared its `RECORD_AUDIO`/`CAMERA` permissions only recently and has never had a call held on real hardware. Treat the whole Android call path as unverified rather than working.

### Identity and onboarding

- **Accounts.** Standard account creation on the official instance; invite-link or invite-code creation with no email on self-hosted servers. Three onboarding entry points (join official, redeem invite, connect to a self-hosted address), with an explicit server-identity fingerprint confirmation step for a manually entered address (trust-on-first-use, not active MITM protection) and a terms-of-use acceptance step at invite redemption.
- **Multi-device.** A day-one requirement, not a retrofit: per-device sessions, refresh-token rotation with reuse detection, and instant revocation from the device list.
- **Account deletion.** Self-service, purges personal data, tombstones the account, and revokes every session. Refuses if you're the last administrator and other members remain (409), which is the only thing standing in for "ownership transfer" (there is no ownership model in the schema to transfer). There is no admin-initiated deletion of someone else's account.
- **Presence.** Online/away/DND/offline with an appear-offline option, told apart by shape rather than color alone. Presence for a channel follows whether you can view that channel.
- **The capability handshake.** `GET /version` reports which safety-relevant capabilities (report, block) a server actually exposes, derived by probing the real router rather than a hand-kept list, so a fork that strips moderation can't silently claim to have it. The sign-in screen warns if they're missing or if the server is too old to say; it never blocks the connection.

### Moderation

- **Roles and permissions.** A 63-bit bitmask, 16 bits defined today (`ADMINISTRATOR`, `VIEW_CHANNEL`, `SEND_MESSAGES`, `MANAGE_MESSAGES`, `MANAGE_CHANNELS`, `MANAGE_ROLES`, `KICK_MEMBERS`, `BAN_MEMBERS`, `CREATE_INVITE`, `ADD_REACTIONS`, `ATTACH_FILES`, `CONNECT`, `SPEAK`, `USE_CANVAS`, `MANAGE_CANVAS`, `MANAGE_SERVER`). Evaluated as `@everyone` base, then role union, then channel overwrites (role-tier deny wins, member overwrite absolute), then the `ADMINISTRATOR` bypass. A roles screen and a per-channel overwrites screen are both reachable from Space settings, gated on `MANAGE_ROLES`.
- **Per-channel permissions, asked correctly.** `GET /channels/{channelId}/permissions` answers the caller's real, per-channel effective bitmask (`docs/decisions/0011-per-channel-permissions.md`), closing a gap where the client used to gate actions like "delete this reported message" on the caller's flat, deployment-wide `GET /me` bitmask - which for a DM report meant offering a delete button the server could never honor, since a DM can never grant `MANAGE_MESSAGES` to anyone. The report card and member popover now ask the right question per action; deployment-wide actions (timeout, removal, role management, invites) still gate on the deployment-wide bitmask, correctly.
- **Timeouts and removal.** A timeout subtracts most permissions (but deliberately not `USE_CANVAS`, so a timed-out member can still see and erase, just not draw) and force-evicts them from any live voice call, including a shared DM call, since a LiveKit token can't be revoked once minted. "Remove from Space" is a durable ban (`space_removals`, reversible from a removed-members screen), gated `BAN_MEMBERS`; it does not stop a fresh account on an open Space.
- **The report queue.** Genuinely actionable, not list-and-dismiss. A moderator can jump to the reported message, delete it (`MANAGE_MESSAGES`), time out the author (`KICK_MEMBERS`), or remove them from the Space (`BAN_MEMBERS`), each action closing the report; each is absent, not just disabled, when the caller lacks the bit. Self-targeting is excluded. The queue itself is pre-filtered by channel visibility before pagination, so a short page always means a short page, including for a moderator explicitly denied `VIEW_CHANNEL` on the reported channel by overwrite.
- **Drag-to-reorder channels and categories.** `MANAGE_CHANNELS`-gated, deployment-wide (one order for everyone, since one deployment is one community), optimistic with a visible revert on failure.
- **Invites and channel management.** Invite creation (including role-granting invites), revocation, and a check that answers expired/spent/revoked/never-issued identically (so codes can't be mined) are all reachable and `CREATE_INVITE`-gated. Channel create/rename/delete is `MANAGE_CHANNELS`-gated; deleting a deployment's last non-DM channel is refused (409).
- **Space usage analytics.** An opt-in, deployment-wide toggle (default off) exposing total messages, messages by day, active hours, and this process's own memory samples - all aggregate, never a per-member breakdown, and derived from `messages.created_at` at read time rather than a background job.
- **What's not there.** No browsable, searchable admin user list or bulk user actions; the closest thing is the ordinary member list everyone can see plus the per-member popover (timeout, remove, assign role), and Space settings' Account recovery pane, which picks a member only to issue them a reset code. No general-purpose `/metrics` route or time-series store (analytics above is a narrower, Space-scoped answer to a related ask, not that). Admin-issued one-time password reset codes are the only account-recovery mechanism, with a known, undecided gap: any administrator can currently issue a reset code for another administrator's account, an impersonation path every other admin-on-admin verb blocks.

### Safety

- **Blocking.** Filters at read time on the client (a blocked author's messages still sync but never render), not at fetch time, because filtering `/sync` itself would make "unblock" unable to bring anything back. Reactions and push notifications are filtered server-side, per viewer, since neither of those can be filtered on-device. A blocked DM says so in the composer and offers Unblock rather than rendering as an empty, unexplained transcript.
- **Reporting.** Any member can report a message or a user, with a 2000-character reason cap shared between reporting and moderation. Feeds directly into the actionable report queue above.
- **No automated content or media scanning.** Owner decision: safety is manual reporting plus the tooling above, not proactive scanning. The official instance's own legal obligation (report known CSAM to the relevant authority on discovery, no proactive monitoring) is documented in `docs/decisions/0001-owner-decisions.md`, with no separate implementation artifact beyond that document.

### Self-hosting

- **Deployment.** One production `docker-compose.yml` at the repo root: server (embedded SQLite on a named volume), Caddy for automatic TLS, LiveKit for voice, and an optional Litestream sidecar. Litestream replicates the SQLite file only; attachment and avatar bytes are not covered, and restoring a Litestream replica brings back message text and attachment *references* but not the files. `scripts/backup.py` and `scripts/restore-drill.py` (documented in `deploy/README.md`) give a real `VACUUM INTO` backup-and-restore drill alongside the Litestream path.
- **CORS.** Opt-in via `SLIMM_CORS_ALLOWED_ORIGINS`; unset means no CORS layer at all, not an empty one; a wildcard origin is refused at startup.
- **Attachment storage ceiling.** `SLIMM_MAX_TOTAL_ATTACHMENT_BYTES` has no default (an operator's disk size isn't something the software can guess); past it, uploads fail with a 507 rather than a 413, so an operator can tell "the volume is full" from "your file is too big."
- **Push notifications.** Content-free by default, encrypted, relayed through a separate stateless Go service that only forwards to APNs/FCM and never sees plaintext. A per-device opt-in (`include_content`) lets the iOS Notification Service Extension - now built - decrypt and show real sender/channel/body text instead of a generic "New message", confirmed working on a real iPhone; tapping that notification also now routes to the right channel via `userInfo` the NSE attaches on-device (Android gets neither the content preview nor tap routing yet, since its envelope is sealed to a key nothing on the device opens). An account-wide notification preference (everything/mentions/nothing) is also settable. Android device wake has never been confirmed on real hardware; that exit criterion remains open.
- **Platforms and packaging.** iOS (TestFlight) and Linux (rpm on Fedora COPR, plus a Flatpak manifest wired into the release) are the platforms actually built and tested day to day. The Linux desktop build also has a real window shell now (`docs/decisions/0012-desktop-window-shell.md`): close-to-tray instead of quitting, a saved-geometry relaunch, and a custom title bar - built, but only automatable up to the point of asserting the process launches and responds; whether the tray icon renders and behaves on a real desktop session is unconfirmed. Android builds and ships to Play's internal testing track but has no confirmed real-device call path. A web build exists, compiles, and is gated in CI, but it's explicitly excluded from v1 scope in `docs/STRATEGY.md` and is used here mainly as a fast way to drive the app in a real browser for testing, not as a released target. macOS and Windows desktop are not built at all.

## What's deliberately not built

From `docs/STRATEGY.md`'s v1 scope and `docs/BACKLOG.md`'s "deliberately out of scope," with the reason each time, so a reader knows these are absent on purpose rather than missing:

- **End-to-end encryption.** Transport-only (TLS) for v1; the server holds plaintext. Per-user and per-device keys are pre-wired so opt-in E2EE DMs can be added later without a wire-format rewrite. Full E2EE was rejected because it breaks history, search, sync, and server-side moderation, and the self-hosting trust model already puts the operator inside the content boundary.
- **Federation between deployments.** One deployment is one community; DMs only work between two people on the same deployment. Not Matrix- or ActivityPub-style federation, and not planned to become that.
- **Multiple communities under one backend.** Same reasoning; revisited only if self-hosters actually ask.
- **Read receipts visible to others.** Deferred as a later opt-in; your own read state already syncs across your own devices.
- **Ringing for an incoming DM call.** Nothing pushes a wake for a DM call the way a message or mention does; a call is only discoverable to someone already looking at the app.
- **Camera background blur or replacement.** Needs a per-frame segmentation model this client doesn't carry; the owner rates it near-required, not started.
- **Rich presence and game status**, a **soundboard**, a **client plugin/scripting system**, a **slash-command framework**, **server-side link unfurling**, an **events/RSVP subsystem**, and **scheduled recurring pings that store PII** are all recorded declines, each because it drifts toward being a Discord clone or opens a real security or maintenance surface the product doesn't need. Webhooks and a future bot API are the sanctioned extension point instead of a plugin system.
- **Heavy ML noise suppression.** WebRTC's built-in echo cancellation and noise filter are used instead, to avoid a native DSP/ML dependency taxing CPU during a call.
- **Automated content or media scanning.** Manual reporting only, by owner decision; see Safety above.
- **A shared media gallery view.** Not built, but cheap to add later since it's only a filtered query over the existing attachment store.

## Where it stands against the roadmap

`docs/ROADMAP.md` is itself annotated with correction passes through 2026-07-28, and some of what it still calls open has since closed; some of what it calls closed was oversold at the time.
Reading the code rather than the annotations:

- **Phases 0 to 3 (foundations, server core, client shell, push).** Solid, and the iOS Notification Service Extension - the one gap that survived every prior correction pass - is now built and confirmed on a real iPhone, opt-in per device. Android push wake still has never been confirmed on hardware, and Android gets neither content previews nor notification-tap routing, since its envelope is sealed to a key nothing on-device opens yet.
- **Phase 4 (voice and screen share).** Built and reachable, including the DM-calling extension the roadmap didn't originally scope, and with the join-lobby UI removed entirely in favor of connecting directly. The aggregate egress bandwidth budget and active-call memory budgets have still never been measured, and device confirmation is still partial: no call has been held on real Android or real iOS hardware.
- **Phase 5 (canvas de-risking spike).** Done for object counts and the R-Tree viewport query; moot now for the rest, since Phase 6 has since shipped real production code covering nearly everything the spike would have de-risked.
- **Phase 6 (canvas full build).** Substantially complete, not "a first slice": place, erase, clear, restore/undo, move, resize, images, text notes, shapes, camera bubbles and screen-share tiles as real movable/lockable canvas objects, multi-user cursors, a text activity log, collapse-to-strip, and a fullscreen mode are all built and reachable. Not chased further: op compaction and a bitmap paint cache for very large canvases, and no convergence property test exists for the write path.
- **Phase 7 (administration, moderation, metrics).** The moderation half is well past what the roadmap credits it for: the report queue is fully actionable and now asks the right per-channel permission question, and threads, reply counts, categories, and channel reordering all shipped as administration-adjacent features the roadmap doesn't name. The metrics half named in this phase's own title is answered narrowly rather than fully: Space usage analytics (opt-in, aggregate-only) exists, but there is still no general `/metrics` route or time-series store.
- **Phase 8 (audio and polish).** Reduce-motion and the desaturated-presence proof are done, and the foreground half of notification sounds now plays for real. Still missing: per-platform background sound behavior, a CallKit ringtone, and Android's versioned notification channels.
- **Phase 9 (release readiness).** The backup drill and the Flatpak manifest both exist now, closing two of this phase's named gaps; a desktop window shell (tray, close-to-tray, custom title bar) also shipped, which the original roadmap never scoped at all. The project still carries its placeholder name. Server and client are both comfortably pre-1.0 (0.37.0 and 0.39.0), and `bump-minor-pre-major` is deliberately keeping it that way so a breaking change doesn't accidentally tag a 1.0 nobody chose.

The overall shape worth taking away: messaging and the canvas have both outpaced their own roadmap language by a wide margin, voice has grown a DM-calling capability and a real window shell the plan never named, and the areas where the roadmap's "not built" is still substantially right are Android's own confirmation story (push wake, calls, content previews) and general-purpose admin metrics.
